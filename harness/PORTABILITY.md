# Перенос учебного harness

Цель — повторить условия запуска и проверяемые ограничения на другом компьютере
или проекте. Одинаковый текст ответа LLM не является критерием воспроизводимости.
Инструкция не включает и не активирует hooks автоматически.

## Что переносить

- `harness/`: политика, подставной runtime, hook-адаптер, тесты и eval-примеры.
- `.agents/skills/review-changes/`: процедура ревью; адаптировать область проверки.
- `AGENTS.md`: использовать как основу, переписав карту проекта и команды тестов.
- `harness/hooks/hooks.example.json`: неактивный шаблон подключения.
- Шаг CI для `harness/tests`: добавить к workflow целевого проекта после проверки
  его зависимостей и Python. Не заменять чужой workflow целиком.

Не переносить `.venv`, секреты, машинные абсолютные пути и записи доверия.
`STATE.md` описывает прошлый проект: новый проект должен получить своё состояние,
а не прошлые разрешения или утверждение о проверенности нового окружения.
`hooks.disabled.json` на этом компьютере — локальный пример, не готовая настройка
для публикации. Убедиться, что шаблон не содержит оставшихся персональных путей.

## Подготовка окружения

1. Зафиксировать ревизию кода (для незакоммиченных файлов — SHA-256), ОС,
   версию Python и зависимости. Установить зависимости целевого проекта
   в его собственное виртуальное окружение по его инструкции.
2. Проверить команды и ограничения политики: учебный allowlist нельзя считать
   универсальной политикой безопасности другого проекта.
3. Из корня проекта запустить локальные проверки:

   ```powershell
   .\.venv\Scripts\python.exe -B -m pytest -q -p no:cacheprovider harness/tests
   ```

4. Проверить обработчик без подключения к coding-среде по `hooks/README.md`.
   Успешный JSON-ответ подтверждает только запуск обработчика.

## Подключение и интеграционная проверка

1. Отдельно согласовать короткое включение строгой политики. Проверить клиент,
   версию, рабочую папку и фактическую среду исполнения (Windows/WSL и shell).
2. Подставить в шаблон абсолютные пути своего Python и обработчика. Учебная
   Windows-команда рассчитана на PowerShell; на другой платформе проверить
   соответствующий вариант запуска. Сохранить все существующие hooks.
3. Настроить проектный `.codex/hooks.json` либо inline hooks, не дублируя одну
   группу в двух форматах. Просмотреть конфигурацию и доверить её штатным способом.
   В Codex CLI для просмотра используется `/hooks`; не обходить доверие и sandbox.
4. В coding-среде вызвать ровно `git status --short`: команда должна выполняться.
   Затем отдельно вызвать ровно `echo HARNESS_BLOCK_DEMO`: должен быть явный
   отказ hook с причиной HARNESS_BLOCK_DEMO до выполнения, без попыток обхода.
   Ручной PowerShell не является проверкой перехвата команд агента.
5. Проверить карточку инструмента/историю hooks: текстовый ответ модели недостаточен.
   При ошибке hook, отсутствии вызова или выполнении echo проверка не пройдена.
   Если используются и CLI, и IDE, проверить каждый клиент отдельно.
6. После демонстрации отключить только нашу группу. Если файл содержит только
   её, переименовать `hooks.json` в `hooks.disabled.json`, начать новую сессию
   и убедиться, что группа больше не активна в используемой среде.

Этот hook блокирует почти все shell-строки, включая pytest; тесты запускать до
активации либо после отключения. Ошибка запуска/timeout hook может не блокировать
вызов: это не полноценная граница безопасности и не замена sandbox.

## Что записать в отчёт

- Дата, ревизия/хеши, клиент и версия, платформа и среда запуска.
- Команда тестов и фактический результат; результаты allow/deny по каждому клиенту.
- Ошибки и непроверенные условия; источник свидетельств (локальная проверка
  или отчёт пользователя). Не записывать токены, полные логи и прежние согласия.
- Состояние после демонстрации: включена ли группа, как её отключили.

Один успешный прогон не доказывает устойчивость. Ручные evals в `evals/README.md`
проверяют поведение агента отдельно от unit-тестов и подключения hook.

Официальный контракт и требования доверия: https://learn.chatgpt.com/docs/hooks
