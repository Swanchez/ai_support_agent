# Учебная проверка команд

`command_policy.py` — независимая функция политики; это ещё не подключённый hook.
Она не вызывает shell, Docker, Git, API или БД и не читает файлы.

Вход — список аргументов, например `["docker", "compose", "ps"]`, а не строка
`"docker compose ps"`. Строку shell нельзя безопасно разбирать простым `split()`.

- `allow`: точная команда из небольшого allowlist.
- `ask`: неизвестная операция или операция, требующая отдельного согласования.
- `deny`: некорректный вход или явно запрещённый запуск shell.

## Структура политики

`validate_arguments` сначала проверяет формат входа. Затем `check_command`
применяет функции из `RULES`: запрет shell, согласование удаления volumes,
точный allowlist. Первое решение завершает проверку. `None` от правила означает
«не подходит», а не разрешение. Если все правила вернули `None`, итог — `ask`.
Новые правила добавляются в явный список с учётом приоритета; порядок проверяется
тестами. Отдельные правила рассчитаны на уже валидированные аргументы.

## Запуск интерактивной демонстрации

Из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m harness.cli
```

Вводите именно JSON-списки, по одному за раз:

```text
["docker", "compose", "ps"]
["docker", "compose", "down", "-v"]
["pwsh", "-Command", "anything"]
```

Первая команда получает `allow` и записывается подставным исполнителем.
Вторая получает `ask`: CLI показывает сохранённые аргументы, рабочую директорию
и идентификатор, после чего принимает `да` или `нет`. Неоднозначный ответ не
считается согласием. Третья получает `deny`, без предложения подтвердить.
Для завершения введите `выход` или `exit`. Завершение ввода во время подтверждения
отклоняет запрос. Директория фиксируется при старте CLI; аргументы не разбираются
как shell-скрипт. Данные хранятся в памяти только до выхода.

CLI использует исключительно `RecordingExecutor`: даже подтверждённое
`docker compose down -v` НЕ запускает Docker и НЕ удаляет данные.

Запуск проверок из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m pytest -q harness/tests
```

Тесты лежат отдельно: стандартный запуск pytest ищет только `tests/`.
В `.github/workflows/tests.yml` добавлен отдельный шаг:

```text
python -B -m pytest -q -p no:cacheprovider harness/tests
```

Он запускается в существующем job после тестов приложения для push/PR в `main`.
Шаг harness не требует API-ключей, LLM, БД, Docker или дополнительных зависимостей.
При падении предшествующего шага обычное выполнение job до него не дойдёт.
Локально на Windows используйте ту же команду с `.\.venv\Scripts\python.exe`
вместо `python`. Настройки поиска тестов проекта не менялись.
Для удалённого запуска нужно включить файлы `harness/` в коммит и отправить
изменения; локальное прохождение не доказывает успешность GitHub Actions.

## Бюджет исполнителя

`CommandRuntime(..., max_executions=3)` ограничивает число вызовов исполнителя
в одном экземпляре runtime. CLI использует значение 3 и показывает расход.
Лимит — целое неотрицательное число; 0 запрещает любые вызовы исполнителя.

- Запрет политики, ожидание подтверждения и отказ пользователя слот не занимают.
- Вызов исполнителя занимает слот, даже если завершается ошибкой.
- Непосредственно перед выполнением проверка и резервирование слота выполняются
  под Lock; параллельные запросы используют общий бюджет экземпляра.
- Подтверждение не обходит бюджет. Если он потрачен, запрос подтверждения всё равно
  потребляется одноразово, но исполнитель не вызывается.
- При исчерпании результат содержит `execution_limit_reached=True`, output отсутствует,
  в трассе появляется `execution_limit_reached`, без `execution_started`.
  Решение `policy` остаётся отдельным: разрешение операции не означает её выполнение.

Для ручной проверки запустите CLI и четыре раза введите
`["docker", "compose", "ps"]`. Первые три вызова будут записаны, четвёртый
остановится из-за лимита. Перезапуск создаёт новую учебную сессию с новым бюджетом.
Это не постоянная квота пользователя: лимиты запросов, токенов, времени,
событий и числа ожидающих подтверждений пока не реализованы. Обход прямым
вызовом исполнителя предотвращается только обязательным маршрутом через runtime;
этот модуль не ограничивает инструменты самой coding-среды.

## Локальная трассировка

`events.py` содержит неизменяемые `TraceEvent` и потокобезопасное хранилище
`MemoryTrace`. `CommandRuntime` записывает события, CLI показывает трассу после
обработки каждой операции, включая отказ. Один `operation_id` связывает начальный
запрос с подтверждением/отказом и выполнением; в учебной версии он совпадает
с идентификатором запроса подтверждения.

События: `command_received`, `policy_allowed`, `policy_denied`,
`confirmation_requested`, `confirmation_accepted`, `confirmation_rejected`,
`execution_started`, `execution_completed`, `execution_failed`, `execution_limit_reached`.
`confirmation_accepted` означает согласие, а не успешное выполнение: новый запрет
может остановить операцию и после согласия. `ask` не создаёт событие завершения
выполнения, пока исполнитель не вызывался.

`duration_ms` измеряет только время вызова исполнителя через монотонный таймер,
не ожидание пользователя и не всю операцию. При обычной ошибке исполнителя
записывается только имя типа исключения; исключение передаётся вызывающему коду.
Нет записи текста ошибки, output, аргументов, директории или причины политики.
Это относится к событиям: интерфейс подтверждения по-прежнему показывает
пользователю точную команду и директорию, необходимые для осознанного согласия.

События хранятся в памяти без ограничения количества до завершения экземпляра.
Нет постоянного audit storage, внешнего экспортёра, временных меток и полного
учёта ошибок инфраструктуры (например, разрешения cwd). Это учебная трасса,
а не производственный аудит. Неизвестные/уже использованные request_id вызывают
исключение, но не добавляют событие к трассе завершённой операции.

## Применение политики в среде

Подготовлен отдельный адаптер `hooks/pre_tool_use.py` и неактивный шаблон
конфигурации. См. `hooks/README.md`: запуск обработчика на искусственном событии,
ограничения и отдельная процедура активации. Пользователь подтвердил блокировку
в CLI и VS Code; временная конфигурация затем переименована в `hooks.disabled.json`.
Инструкция переноса: [PORTABILITY.md](PORTABILITY.md). Прохождение локальных тестов
не означает, что новый клиент загрузил hook.

`runtime.py` демонстрирует применение политики в учебной среде:
`CommandRuntime.run` сначала вызывает `check_command` и только при `allow`
обращается к исполнителю. При `ask` и `deny` возвращает решение без выполнения.
`RecordingExecutor` лишь сохраняет копии команд в памяти — процессов нет.
Тесты проверяют, что остановленные команды вообще не вызывают исполнителя.
При `ask` возвращается неизменяемая запись `pending`: идентификатор запроса,
аргументы, абсолютная рабочая директория и причина согласования. `deny` не
создаёт такой записи. Подставной исполнитель также записывает директории.

```python
from harness.runtime import CommandRuntime, RecordingExecutor

runtime = CommandRuntime(RecordingExecutor())
result = runtime.run(["docker", "compose", "down", "-v"], cwd=".")
# Доверенный UI показывает result.pending пользователю и получает согласие.
confirmed = runtime.confirm(result.pending.request_id)
# Это только запись в память, а не реальный запуск Docker.
```

`confirm` не принимает новые аргументы или директорию. `reject` отклоняет запрос.
Оба метода потребляют идентификатор одноразово; повторный или неизвестный запрос
вызывает `ConfirmationNotFoundError`. При подтверждении запреты проверяются
повторно. Идентификатор удаляется до вызова исполнителя, даже если тот завершится
ошибкой. Это не гарантия exactly-once при сбоях внешней системы.

Записи хранятся только в памяти экземпляра, без срока жизни и постоянного
хранения. Пример рассчитан на одного доверенного пользователя: нет аутентификации,
проверки владельца запроса; CLI — лишь локальная демонстрация интерфейса.
`confirm` нельзя предоставлять модели
как инструмент: знание идентификатора само по себе не доказывает согласие человека.
Для сетевого/многопользовательского адаптера эти проверки обязательны.
Это не hook, подключённый к Codex или другой внешней coding-среде.

Адаптер `hooks/pre_tool_use.py` сопоставляет только точные shell-строки с argv
и обращается к общей политике. Он не использует runtime или его confirm:
неизвестные строки блокируются, `ask` в ответ PreToolUse не передаётся.
Для отдельного адаптера runtime среда должна остановить действие при `ask` и `deny`.
Подтверждение привязывается к точной операции, аргументам и рабочей директории,
а не превращается в разрешение на любые следующие команды.

Это демонстрация, а не готовая граница безопасности. Она не анализирует shell,
пути к исполняемым файлам, конфигурацию Git/Docker или рабочую директорию.
Альтернативная запись опасной команды может получить `ask` вместо `deny`,
но не должна автоматически выполняться. Нужны sandbox и ограничения среды.
Даже команды из allowlist следует запускать только в доверенном окружении.
Реальные настройки coding-среды и разрешения этим модулем не изменяются.
